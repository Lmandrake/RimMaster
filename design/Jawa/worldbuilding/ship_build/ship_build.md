## ⚠️ Read this before you build

### 1. The engine is the ANCHOR, not cargo — extenders probably ride along

The shipped example (`Advanced_Starter_Ship.xml`) has **35 distinct defs and
neither `GravEngine` nor any `*Extender*` among them.** `PilotConsole` is.

That example is only 354 tiles — inside one engine radius — so it never needed
extenders, and **cannot by itself tell us whether they export.** So I read the
mod's own assembly. Its string table is decisive about the engine and strongly
suggestive about extenders:

```
"ExportV2: Starting BuildLayout for engine at {0}."
"ExportV2: engine was null. Aborting export."
"No need to temporarily expand GravEngine facility range, ran…"
"Finished building sketch. Structural cells={0}, things added…"
```

**Established:** the export is *anchored on the grav engine* and aborts without
one. The engine is the origin of the capture, which is exactly why it is absent
from the things list — a ship does not carry its own anchor; the new game
re-creates it. That also means **you must build the engine before exporting**,
and it need not be re-placed on import.

⚠️ **Inference, not proof — flagged as such:** `Extender` appears **nowhere** in
the assembly, in either encoding. No special-casing means extenders are treated
as ordinary buildings on the substructure footprint, and ordinary buildings
demonstrably export. The third string is the encouraging one: the exporter
already *temporarily expands the engine's facility range* to capture a ship
larger than one radius, so large hulls are an anticipated case.

**Still worth the cheap test first:** export a *small* ship with one extender,
re-import, look. Five minutes against a 4,057-tile build.

_(Method note: the first scan of this assembly found nothing because it searched
UTF-8 only. .NET string literals are UTF-16 in the `#US` heap — the same trap,
inverted, that `verify_gm_gate` already checks both encodings for.)_

### 2. The engine can sit at the shrine-heart — it costs one extra extender

The published 7-extender solution puts the engine at **(55, 34)**, on cargo,
because the solver maximises coverage and does not care about the fiction. The
deck plan wants it at the **shrine-heart**. Both work:

| engine at | extenders | coverage | note |
|---|---|---|---|
| **(55, 34)** solver optimum | **7** | 100% | ignores the fiction |
| **(45, 92)** shrine-heart ⭐ | **8** | 100% | what the deck plan describes |

Cap is 12, so **take the shrine-heart.** One extender is a cheap price for the
ship's whole premise sitting at its centre.

Shrine-heart placement, verified 100% coverage, 0 uncovered:

```
ENGINE (45, 92)          <- the scrap-totem shrine, dead centre
EXT    (45, 58)  (55, 30)  (45,114)  (11, 92)
       (79, 92)  (56,  8)  (35, 39)  (55, 39)
```

⚠️ **Every node must stand on a backbone tile inside the already-connected
field** — the chain rule. The list above satisfies it in the order given, so
**place them in that order.**

✅ **The one collision is FIXED.** `EXT (45, 58)` sat on a keel tile that also
took an exposed `PowerConduit` — `GenSpawn` would have wiped or refused it, and
the symptom is a missing extender with nothing in the log. The generator now
places `HiddenConduit` wherever a keel tile also carries a building or a node,
and `PowerConduit` in the open. Asserted in the selftest: *no node sits on
exposed conduit*.

⚠️ **Honest note on the ratio.** The exporter's example is 64% hidden (90/50).
Ours comes out **1 hidden / 184 exposed** — not because the rule is wrong but
because a long open keel has almost nothing built on top of it, whereas that
example is a small dense ship where most conduit runs under rooms. **The rule is
matched; the ratio is not, and should not be.** Copying 64% would mean hiding
conduit for no structural reason.

### 🆕 The bridge could not orient a door until tonight

Auditing this exposed a real gap: `jawa/spawn_batch` had **no rotation support at
all**. Every spawned thing landed at the default facing. Not a corner case for a
ship — the exporter's own example has **45 of its 380 things rotated** (doors,
thrusters, beds, chairs).

Fixed and **deployed** (`2f74209`): `rot` 0–3, call-level, mirroring `stuff`.
Batch by facing — every steel wall in one call, every east-facing door in the
next. Live from the next game start.

### 🔴 Three machines must be rotated BY HAND

`Conveyor Oven`, `Cannery`, `Autoloom` are placed 90° rotated, and **a footprint
cannot tell east from west** — both give the same rect. They are emitted at
`rot=0` and flagged `needsManualRotation` in `ship_bridge.json` rather than
shipped at a confident default that would be wrong half the time.

**Rotate those three after placing them.** Everything else is `rot=0` and correct.

### Machine footprints and rotation — recovered, not dropped

The first version placed each machine at its rect **anchor** and threw away the
footprint and facing. Both are now carried:

* **261 footprint cells** are recorded (18 anchors + 243 marked `occupiedBy`), so
  nothing else can claim a cell a machine already stands on.
* **3 of the 18 are rotated 90°** — **Conveyor Oven**, **Cannery**, **Autoloom**.
  Derived, not guessed: `build_sheet_15.py`'s packer tries both `(w,h)` and
  `(h,w)`, so a placed rect whose dimensions are swapped against the declared
  `MACHINES` size *is* a rotation. The declared sizes are parsed from that source
  file rather than retyped, so the two cannot silently desync.

⚠️ **A footprint cannot distinguish EAST from WEST** — both are 90° and give the
same rect. The sheet says *"rotated"*, not a specific `Rot4`, because guessing a
facing would be wrong half the time.

**Checked, and clean:** across all 18 machines — 0 cells off the hull, 0 on a
hull wall, 0 overlapping each other, 0 outside their own wing, and 0 clashes with
the 51 hoppers / 8 heatsinks / 2 boosters. The packer's 1-tile halo did its job.
