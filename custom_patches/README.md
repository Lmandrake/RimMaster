# custom_patches/ — self-authored compat patches (last resort)

Local RimWorld mod holding **only** patches we author for the gravship campaign.
Load it **last** in the mod order (RimSort) so it sees the final state of every
def it touches.

## Standing preference: avoid patches when possible

Patches are a debugging tax — a mistyped xpath fails **silently**, load order
can move the target out from under you, and VEF/VFE updates rename defs between
versions. So the rule for this folder is:

1. **Prefer an existing maintained mod** that does the same thing. Only author a
   patch when no clean mod exists (or the mod is stale on the current game
   version).
2. **Wrap every patch in `PatchOperationConditional`** whose test also checks the
   target isn't already in the desired state. That turns "target moved / already
   handled" from a red error into a silent no-op.
3. **Never guess a defName or field.** Every target here was read from the
   actual mod source before writing the patch.
4. **Test in a dev-mode throwaway world** and read `Player.log` before trusting
   a patch in the campaign save.

## Deployment — READ THIS BEFORE TESTING ANYTHING

**This folder is not what the game reads.** RimWorld loads its own copy from

```
C:\Program Files (x86)\Steam\steamapps\common\RimWorld\Mods\<ModName>
```

and says so in `Player.log` on every launch:

```
Adding mandrake.jawa.patches(C:\...\RimWorld\Mods\Jawa_Patches)
```

Nothing syncs the two automatically. **Editing only this folder means the change
silently never reaches the game** — no error, no red text, the def simply is not
there. That is exactly what happened on 2026-08-11: a Gamorrean xenotype and its
pawnkinds were authored here, reported ready to test, and were invisible in game
because the deployed copy was untouched. A whole test cycle was spent on it.

Treat **"the file is written"** and **"the game can see it"** as two separate
claims. The second one needs this:

```bash
python Utils/deploy_custom_mods.py            # plan only — shows drift, changes nothing
python Utils/deploy_custom_mods.py --apply    # copy repo -> game, then self-verify
```

The script is safe by default (plan-only), covers all four mods, skips
authoring-side files (`Source/`, `*.py`, `README.md`), warns when a mod is not
enabled in `ModsConfig.xml`, verifies every copy afterwards, and exits non-zero
while drift remains — so it also works as a pre-flight check before a test
session. Other flags:

- `--mod Jawa_Patches` — limit to one mod
- `--prune` — with `--apply`, delete deployed files no longer in the repo
- `--pull Jawa_Patches` — reverse direction, rescuing an edit made directly in
  the game folder before this script overwrites it

### Then restart RimWorld

Defs are parsed **once at startup**. Reloading a save will not pick up new XML.
Adding brand-new defs (a new xenotype, a new pawnkind) is safe for an existing
save; changing or removing a def a save already references is not.

### Then test properly

Dev-mode throwaway world, spawn the thing, and read `Player.log` for patch errors
before trusting any of it in the campaign save.

### Four threads work in this repo

Deploy is a shared, destructive-ish step: `--apply` overwrites the game copy with
whatever is in the repo right now, including another thread's half-finished work.
Run the plan first and read it. If you see `-` lines (present in the game, absent
from the repo), someone hand-edited the deployed copy — `--pull` it back before
overwriting.
