# WSL "crashes" — diagnosed: one Claude Code seat OOMs the whole VM

**Status: ✅ ROOT CAUSE PROVEN. Per-seat bound INSTALLED 2026-08-14 — all five
Windows Terminal profiles now launch through `claude_bounded.sh`, so any tab
opened from here is protected. `.wslconfig` (36 GB) still needs `wsl --shutdown`.**
Measured 2026-08-14. **Two occurrences, both on 2026-08-14** — not three. The
Aug 13 02:44 restart was Windows Update (`TrustedInstaller.exe`, Event 1074);
WSL boot `-4` logged **zero** OOM kills and ended on a clean `poweroff.target`.
Corrected after the fact: the "third time this week" was a different event.

---

## Symptom, as experienced

All five Claude Code seats die at once. The owner reboots Windows to recover. It
had been attributed to "WSL running out of memory" with no measurement behind it,
and separately — wrongly — to GPU pressure.

## What it actually is

```
Aug 14 11:26:41 kernel: HTTP Client invoked oom-killer: gfp_mask=0x140cca, order=0
Aug 14 11:26:41 kernel: oom-kill:constraint=CONSTRAINT_NONE, ..., global_oom, task=2.1.232, pid=25380
Aug 14 11:26:41 kernel: Out of memory: Killed process 25380 (2.1.232)
                        total-vm:38083000kB, anon-rss:27445504kB
```

`2.1.232` is `~/.local/share/claude/versions/2.1.232` — **the Claude Code binary,
named by version.** One seat held **27.4 GB** of the VM's **31.7 GB**. Its five
siblings, from the same OOM table, held ~300–400 MB each:

| pid | RSS | process |
|---|---|---|
| 25380 | **27.4 GB** | `2.1.232` ← one seat |
| 12890 | 2.5 GB | `python3` (repo tooling) |
| 4628 / 1662 / 1209 / 908 / 692 | ~386 / 377 / 297 / 269 / 230 MB | `claude` |

`constraint=CONSTRAINT_NONE` + `global_oom` means the **VM** ran out, not a cgroup —
so init went down and took every seat with it. That is why all five die together;
a per-process OOM kill would have taken only one.

**Same pattern the night before**, boot `-3`, which explains the 01:43/01:44/01:50
VM churn:

```
Aug 14 01:37:27 kernel: Out of memory: Killed process 3151 (2.1.232) anon-rss:20455936kB
Aug 14 01:38:36 kernel: Out of memory: Killed process 3151 (2.1.232) anon-rss:20455936kB
Aug 14 01:40:25 kernel: Out of memory: Killed process 3151 (2.1.232) anon-rss:20455936kB
```

### Trigger, per the owner

Both events had **RimWorld running, all five seats up, and seats spawning
subagents**. Subagent contexts accumulate inside the *parent* seat's single
process — which is exactly the shape of the data: one process at 27 GB, siblings
at 600 MB. The project's standing "fan out freely, do not ask" authorization is
what drives a seat there.

## Swap does not save you — it buys 115 seconds

Free swap, boot `-1`, from the journal:

| time | free swap |
|---|---|
| 11:19:48 | 8,370,456 kB (untouched) |
| 11:20:14 | 7,067,864 kB |
| 11:21:26 | 2,213,956 kB |
| **11:21:43** | **0 kB** |
| 11:26:41 | 0 kB — the kill |

Pid 25380's own OOM-table row shows `swapents:1879328` pages = **7.2 GB of swap
held by that one process**. Swap went from full to empty in **1 min 55 s**, and
the VM then limped for **five minutes with none left** — that is the "completely
hosed" window, not the kill itself. Raising `swap=` buys minutes, not safety.

⚠️ Swap free is a *sharper* alarm than RSS growth and is now sampled by
`resource_watch.sh`, which fires CRITICAL below 25%.

## 🔴 Recovery: `wsl --shutdown`, not a reboot

The VM's last journal entry on boot `-1` is **11:28:21**. The Windows reboot was
**12:06:21** — **38 minutes later**. Rebooting Windows was never necessary: once
the VM is dead, `wsl --shutdown` from PowerShell recovers it in seconds and picks
up any pending `.wslconfig` at the same time. Thirty-eight minutes of that outage
was avoidable.

## The fix

The ceiling was never the problem — **a process that reaches 27 GB will reach
40 GB.** What was missing is isolation: all five seats shared **one unbounded
cgroup**, `/init.scope` with `memory.max=max`, because `wsl.exe -- bash -lc`
never opens a per-session scope.

**`src/RimMandrake/Utils/claude_bounded.sh`** launches each seat in its own scope
with `MemoryMax=6G`, `MemorySwapMax=2G`. Verified on this machine by deliberately
overrunning a 200 MB scope:

```
oom-kill:constraint=CONSTRAINT_MEMCG, oom_memcg=/user.slice/.../run-p10162.scope
Memory cgroup out of memory: Killed process 10482 (python3)
```

`CONSTRAINT_MEMCG` instead of `CONSTRAINT_NONE` **is the entire fix** — the
offending seat dies, the VM and the other four survive.

⚠️ **`MemorySwapMax` is not optional.** With swap unbounded the same test was not
killed at all; it spilled into the 8 GB swap and kept running. That is the seven
minutes of page-allocation failures (11:19:48 → the 11:26:41 kill) during which
the machine is unusable but not yet dead.

**Budget:** 5 seats × 6 GB = 30 GB + ~3 GB python3 tooling < 36 GB VM. Even all
five ballooning simultaneously cannot reach a global OOM.

`C:\Users\Mandrake\.wslconfig` — written this session, **needs `wsl --shutdown`**:
`memory=36GB`, `swap=16GB`, `[experimental] autoMemoryReclaim=gradual`.

### Installed, and what it took

`LAUNCH` at `src/RimMandrake/Utils/install_wt_seat_profiles.py:103` now points at
`claude_bounded.sh`; `--apply` wrote all five profiles (backup beside
`settings.json`). Verified after the fact: every `AGENT *` profile's
`commandline` contains the wrapper, a TTY survives the scope
(`STDIN_TTY_OK`/`STDOUT_TTY_OK` under `script`), and a launched process lands in
a scope with `memory.max=6442450944` / `memory.swap.max=2147483648`.

🔴 **The wrapper's first guard was wrong and would have silently defeated it.**
It gated on `systemctl --user is-system-running`, which on this machine reports
**`degraded` and exits 1** — a perfectly normal state — while scope creation
works fine. Every seat would have started UNBOUNDED with only a one-line stderr
notice that scrolls past in a fresh tab. It now probes the capability directly
(`systemd-run --user --scope --quiet -- true`) and shouts in red for three
seconds if it ever has to fall back.

**Generalises to:** when a guard protects something expensive, test the
capability itself, never a status string that summarises it.

## Watching it live

`src/RimMandrake/Utils/wsl_monitor.ps1` — a small always-on-top readout of
`vmmemWSL`, green/amber/red, refreshing every 5 s. It runs on **Windows**, not in
the VM: during the 6m53s of thrashing the host stayed fully responsive while
anything inside the VM was competing for the memory that had just run out. No
dialogs; the colour is the notification. Install it as a logon task with the
`schtasks` line in its header.

🔴 **`dmesg` is wiped by a WSL restart. `journalctl --list-boots` is NOT** — it
persists across them, and boots `-1` and `-3` are where every quote above came
from. Reach for journalctl first next time; the evidence was never actually lost.
