## 🔴 Ground hulk — the GenStep ran and found nowhere to go

**The game says so itself**, which is the whole finding:

```
Scatterer Verse.GenStep_ScatterGroupPrefabs from def
Jawa_StampGroundHulk could not find cell to generate at.
```

**Two maps out of two**, same line both times.

Everything upstream is fine and was checked rather than assumed:

| def | type | resolves live | owning mod |
|---|---|---|---|
| `Jawa_StampGroundHulk` | GenStepDef | ✅ | Jawa Patches |
| `Jawa_GroundHulk` | PrefabDef | ✅ | Jawa Patches |
| `Jawa_ScatterScrapfields` | GenStepDef | ✅ | Jawa Patches |
| `BrokenSubstructure` | TerrainDef | ✅ | Gravship Crashes |
| `Base_Player` | MapGeneratorDef | ✅ | Core |

Map evidence: **zero** `BrokenSubstructure` or `Substructure` cells in a full
250×250 terrain scan; **zero** `AncientCryptosleepCasket` in an 8,100-cell sample.

**So this is placement, not registration.** The patch applied, the GenStep is in
`Base_Player`'s list, it executed, and it rejected every candidate spot.

⚠️ **The first map was hostile and the second was not.** Map 1 was volcanic
coastal — `LavaFlowBasalt`, `PassableBasalt`, `WeatheredBasalt`, `BeachRock`,
`WaterOceanDeep/Shallow`. Map 2 carried `Sand`, `SoftSand` and `TileSandstone`
in quantity. **Both failed identically**, which is what moves the diagnosis off
"unlucky tile".

**Suspect, for CREATE to test — not a conclusion I can reach from here:** the
constraints together are demanding on a 250×250 map — a **73×16** footprint with
**`minSpacing 85`**, `spotMustBeStandable true`, `allowRoofed false`, and
`ScatterValidator_AvoidUsedRects` at **order 940**, by which point earlier
scatterers have already claimed rects. `minSpacing` is the first thing I would
halve.

✅ **Note what this is NOT.** CREATE's predicted failure was *"deck present, props
absent"* from a `BrokenSubstructure` affordance problem. That prediction was
already struck offline — `ShipChunk_Mech` needs `Light`, not `Heavy`, and
`BrokenSubstructure` supplies Light/Medium/Heavy/Walkable/Substructure by list
merge with `FloorBase`. The real failure is one step earlier and has nothing to
do with affordances.

## 🟠 Scrapfields — not demonstrated, and the sample says why

9 rects of 30×30 = **8,100 cells**, ~13% of each map.

| | map 1 (volcanic) | map 2 (sandy) |
|---|---|---|
| `ChunkSlagSteel` | 1 | 1 |
| `Filth_MachineBits` | 4 | 4 |

Extrapolates to **~7 chunks map-wide** against the plan's **75–125** band.

⚠️ **The counts are IDENTICAL across two completely different maps**, which is the
tell: a `countPer10kCellsRange 12~20` scatter would vary. **These are almost
certainly background objects from other generators, not ours** — so the honest
verdict is *not demonstrated*, not *failed*, and certainly not *passed*.

Unlike the hulk, `Jawa_ScatterScrapfields` logs **nothing at all** — no placement
complaint. A `GenStep_ScatterThings` that places few things is silent by
construction, so absence of a log line is not evidence either way here.

**To settle it:** a count on a map where our scatter is the only source, or a
temporary `countPer10kCellsRange` raised far enough that ours cannot be confused
with background. Not runnable without a def edit, which is CREATE's.

## Method notes worth keeping

- **`mapCount > 0` is not a drivable map.** Measured: `mapCount` went 0 → 1 a
  full **~30 s** before `currentMapReady` went true.
- **`start_debug_game_ready` exceeds the 30 s client timeout and succeeds
  anyway.** Never retry — a retry is a second map.
- **The companion is unusable at a main menu.** Every `jawa/*` tool ends
  `Find.TickManager?.TicksGame ?? -1`; `Find.TickManager` compiles to
  `Current::get_Game` + `ldfld Game::tickManager`, so with no game the **getter**
  throws and `?.` does not help. Every tool returns a bare
  `Object reference not set to an instance of an object`. Diagnosed because
  `ThingDef/Steel` failed identically to `BiomeDef/Desert` — a control that was
  already to hand.
