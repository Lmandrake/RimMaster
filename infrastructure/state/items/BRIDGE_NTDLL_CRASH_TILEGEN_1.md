## spec
Filed by FOUNDRY, 2026-09-05, during a live-verify session for
`TILEGEN_SILENT_REUSE_1`. RimWorld crashed TWICE in one session with an
**identical fault signature**:

```
Faulting module name: ntdll.dll
Exception code: 0xc0000005 (access violation)
Fault offset: 0x0000000000070f32          <- SAME both times
```

Both crashes happened on the full 595-mod list, shortly after a
`rimworld/start_debug_game_ready` quicktest start:

- **Crash 1** (06:21:26): during/shortly after the quicktest's own scenario
  setup (heavy dev-start content: entire tech tree auto-completed by "Isekai
  Leveling", many pawns force-generated by "Isekai Forge"). No
  `world_tile_map_generate` call had been made yet this connection.
- **Crash 2** (06:49:17): immediately after calling `jawa/world_tile_map_generate`
  for tile 300 on a FRESH quicktest map (mapCount was 1 before the call). The
  client's own connection reset with a 30s-class timeout right as the crash
  hit — consistent with the crash happening server-side mid-call, not a client
  bug.

## What this is NOT (yet)
Not confirmed to be caused by anything deployed this session. The fault is in
`ntdll.dll` — a raw native access violation, not a managed .NET exception —
so a bug in the 4 C# assemblies redeployed this session (JawaBench.BridgeTools,
RustChrome, StructureInjections, Inhabited) would much more likely surface as
a `TypeLoadException`/managed stack trace in `Player.log`, not this. Neither
crash left ANY exception trace in `Player.log` before the connection died —
the log simply stops.

## Why this might matter to TILEGEN_SILENT_REUSE_1
`TILEGEN_SILENT_REUSE_1`'s original defect is `world_tile_map_generate`
silently returning a fabricated success for a second, different tile instead
of actually generating it. **One plausible unifying explanation**: whatever
`MapGenerator.GenerateMap`/GenStep call sometimes corrupts state badly enough
to crash outright (this session, twice) might on other runs corrupt state
just enough to return stale/wrong data without crashing (the original
2026-09-04 report). This is a hypothesis, not a finding — per
`[[one-negative-is-not-a-mechanism]]`-class doctrine, it needs the actual
crash dump or a WinDbg/minidump analysis to confirm, not more guessing from
symptoms.
