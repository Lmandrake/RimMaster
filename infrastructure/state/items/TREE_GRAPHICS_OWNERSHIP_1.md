Owner, verbatim (filed on the item): *"Rather than use the whole Comingo tree

### Part 1 — our own tree, our own scale

New mod `src/RimUtinni/AshkarrFlora/` (`mandrake.rut.ashkarrflora`), ships:

- `Defs/ThingDefs_Plants/RUT_AshkarrFlora_Plants.xml` — `RUT_SweetlineTree`,
  `ParentName="TreeBase"` (not `DeciduousTreeBase` — this world has no
  day/night or season cycle, so the fall-colour shader params don't apply).
  `plant.visualSizeRange` `5.0~6.5` (a canopy 5-6.5 tiles wide at full growth —
  bigger than vanilla's biggest common tree, `Plant_TreePine` at up to 6.0
  under the BetterTrees Djeeshka template). `Flammability` cut to `0.1`
  (arid_shrubland.md §6 rule 9, hard ban on flammable living flora — not
  optional). `wildClusterRadius`/`wildClusterWeight` cut near to zero — this
  tree does not cluster or scatter randomly; see the wildPlants decision
  below. `growDays`/`harvestWork` raised well past `TreeBase` defaults as
  flavour for "ancient"/"huge"; that is NOT a balance pass.
- `Patches/BetterTrees_SweetlineTree_Immunity.xml` — see Part 2.
- Art: **NOT YET GENERATED — blocked, see Owed.** `graphicData.texPath` points
  at `Things/Plant/RUT_SweetlineTree` (a `Graphic_Random` directory, vanilla
  convention: `RUT_SweetlineTreeA.png` etc.) but the directory is currently
  empty. The def loads and validates without it; RimWorld would show a
  magenta/missing-texture tree until art lands.

**Judgment calls made (owner's ruling didn't specify these; documenting
per FOUNDRY doctrine):**

1. **Not wired into `wildPlants`.** The biome doc says each sweetline tree
   "grows only on the optimum... a living surveyor's mark, visible for a day's
   walk... every one has a name" — that is a *hand-placed landmark*, not a
   commonality-weighted random spawn. Adding it to
   `src/RimUtinni/UtinniPatches/Patches/BiomeFlora_Ashkarr.xml`'s
   `AridShrubland` wildPlants (even at a tiny weight) would scatter multiple
   random, unnamed instances across every shrubland tile cluster — wrong
   shape for "one per named location, roads follow them." That file is also
   generator-owned ("GENERATED by design/Jawa/mods/biome_flora.py — do not
   hand-edit"), so it should not be hand-edited regardless. Placing named
   sweetline trees along the actual sweetline contour is a **world-editing
   task**, not a def-authoring one — filed as Owed below.
2. **Single-tile footprint, oversized visual only.** "Huge, ancient" is
   delivered via `visualSizeRange` (visual scale only, matching how vanilla's
   own biggest trees work) rather than a multi-cell `size`. A true monumental
   multi-tile object (giants physically rubbing against it, roads terminating
   at it, a name/label UI) is a separate engineering lift — the biome sheet's
   own "Owed" list already calls this out ("Engine feasibility pass... this
   biome needs its own"). This ticket closes the ART/SCALE-OWNERSHIP half
   only.
3. **Choppable, default `TreeBase` interaction kept.** Whether a
   one-of-a-kind named landmark tree should be choppable/killable by a
   colonist at all is a gameplay-design call the owner hasn't made; left at
   vanilla `TreeBase` defaults (choppable, yields `WoodLog`) rather than
   inventing an "indestructible landmark" mechanic unasked.
4. **Numeric stat bumps are flavour, not balance.** `MaxHitPoints` 650,
   `Mass` 900, `BeautyOutdoors` 10 — picked to read as "huge and ancient,"
   not tuned against any economy.

### Part 2 — the rescaling mechanism, found and neutralized

Read from the live Workshop copies (mod IDs come from the live
`ModsConfig.xml`, not guessed):

| packageId | workshop id | role |
|---|---|---|
| `ChaoticEnrico.BetterTrees` | `3539609975` | the framework. Harmony DLL (`1.6/Assemblies/BetterTrees.dll`) plus two custom Def types, `BetterTrees.TreeScaleTemplateDef` and `BetterTrees.TreeTextureTemplateDef`. |
| `Qux.Comigo.BetterTreesMod` | `3559784361` | "Comigo" — a texture pack that feeds the framework (`loadAfter: ChaoticEnrico.BetterTrees`). This is the "whole Comingo tree thing" the owner named. |
| `Maal.BetterTreesMod` | `3543705507` | a second texture pack, same framework, recolors/variants "originally drawn by Djeeshka and Comigo." |

**Mechanism** (confirmed from `Defs/BetterTrees/DjeeshkaTemplates.xml`, the
framework's own shipped template): `TreeScaleTemplateDef.treeScales` is a
flat list of `<li><defName>X</defName><minScale>..</minScale><maxScale>..</maxScale></li>`
— **keyed strictly by exact `defName`, no category/thingClass/tag wildcard.**
`minScale`/`maxScale` are the same shape as vanilla's own
`PlantProperties.visualSizeRange` (`Source/RimWorld/PlantProperties.cs:147`,
`FloatRange`, default `0.9~1.1`, consumed by `Plant.cs:863`/`961` via
`LerpThroughRange(growth)`) — strong circumstantial evidence the framework's
Harmony patch overrides that exact field per-defName rather than inventing a
new one. `TreeTextureTemplateDef.treeTextures` is the same shape for texture
directory overrides. Neither template carries a wildcard/"all trees" entry.

⇒ **A brand-new defName absent from all three mods' shipped templates is
structurally immune already** — no uninstall, no incompatibility declaration,
nothing else required. `RUT_SweetlineTree` does not appear in any of the three
mods' data (checked by reading their shipped `Defs/BetterTrees/*.xml` in the
Workshop tree directly — none list it, trivially, since it did not exist
before tonight).

**What was shipped anyway, as insurance:**
`src/RimUtinni/AshkarrFlora/Patches/BetterTrees_SweetlineTree_Immunity.xml` —
two `PatchOperationConditional` (`MayRequire="ChaoticEnrico.BetterTrees"`)
blocks that `PatchOperationRemove` any future `<li>` naming
`RUT_SweetlineTree` out of either template's dictionary. **Validated
offline, matches 0 nodes today — that is correct and expected** (none of the
three mods currently mention our defName), not a defect. If any of them ever
ships an update that claims our name, this patch neutralizes it without
anyone having to notice first.

**Deliberately NOT done, and why:** did not touch `ModsConfig.xml`, did not
disable/uninstall the three mods, did not write a blanket
"BetterTrees, stand down for every RimUtinni tree" patch. The owner's
complaint was specifically about **our own designs** being rescaled to
unpredictable values; vanilla and other mods' trees being retextured/rescaled
by a mod the owner is still subscribed to is outside this ticket's scope
unless/until he says he wants BetterTrees gone entirely. That would be a
mod-list change (touches the live game's next load) and is exactly the kind
of call this pass was told not to make unilaterally overnight.
